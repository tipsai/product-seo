## 1. Главная идея

Цель SEO для продукта: регистрации из поиска. Показы и клики только подсказывают, туда ли мы идём.

Отсюда правила, которые действуют всегда:

- Сначала данные. Смотрим, что люди на самом деле ищут, а не гадаем.
- Судим по регистрациям, а не по трафику.
- Перед тем как что-то делать, смотрим выдачу: если в топе стоят тулы, статья туда не встанет.
- Лучше меньше страниц, но сильных. Одна страница, которая отвечает на запрос лучше нынешней первой десятки, полезнее десяти, которые её повторяют. За эти месяцы мы убрали и склеили больше слабых страниц, чем опубликовали новых.
- Факты не выдумываем. О своём продукте пишем только по файлу фактов, о чужих только по их официальным страницам, с цитатой, ссылкой и датой.
- Цифры из данных пользователей в публичные тексты не берём. Такая цифра говорит читателю: «мы смотрим ваши данные».
- Всё, что уходит на сайт или наружу, одобряет человек. Заявки и письма отправляет человек.
- Перед правкой сохраняем старую версию. Правку записываем вместе с датами проверки.

## 2. С чего начать: две кучи

Берём из Search Console запросы и страницы за последние 1–3 месяца. Запросы с названием продукта откладываем: эти люди и так шли к вам.

Остальное собираем в темы и про каждую задаём один вопрос: **продукт и есть ответ на этот запрос?**

- **Куча А: да.** У человека та задача, которую решает продукт. Он может зарегистрироваться в тот же заход.
- **Куча Б: нет.** Человек прочитает и уйдёт.

Если есть данные о регистрациях по страницам, решаем по ним. Если нет, представляем, как человек доделывает свою задачу: будет ли у него в этот момент открыт ваш продукт?

Кучи показываем владельцу. Он лучше знает, кто платит.

Скорее всего, результат будет неприятный. Обычно большинство кликов оказывается в куче Б, а темы из кучи А стоят на второй странице выдачи. Это и есть главная находка: лёгкий трафик не превращается в клиентов, а ценные запросы близко.

Порядок работы внутри кучи А:

1. Страницы на 8–20 месте. Их проще всего поднять на первую страницу.
2. Страницы на первой странице, по которым мало кликают.
3. Страницы, которые мешают друг другу по одному запросу.
4. Запросы, под которые страницы нет.

Перед работой над страницей смотрим её динамику по неделям. Растёт сама: не трогаем. И проверяем сезон: некоторые темы падают каждый год в одно и то же время.

Слова для заголовка выбираем по спросу. Одну формулировку ищут в разы чаще синонима, и угадать это нельзя, надо смотреть. Смотрим и тренд за год: большая цифра, которая за год упала вдвое, уже другая история.

**Если сайт новый** и его ещё нет в Search Console или показов почти нет, план на первый месяц такой.

*Первая неделя: чтобы сайт нашли и чтобы было что считать.*
1. Подключить Search Console: на search.google.com/search-console добавить «Доменный ресурс» и подтвердить его записью TXT в DNS у регистратора домена. Если DNS недоступен, подойдёт «Ресурс с префиксом в URL» с подтверждением через HTML-тег или файл.
2. Там же отправить карту сайта (обычно `/sitemap.xml`, конструкторы делают её сами) и в «Проверке URL» запросить индексирование главной. Это кнопка, нажимает её владелец.
3. Добавить сайт в Bing Webmaster Tools импортом из Search Console и настроить IndexNow.
4. Проверить, что сайт открыт для поисковиков: не осталось `noindex` от разработки, `robots.txt` ничего не закрывает, у каждой страницы свой заголовок и описание, сайт нормально выглядит на телефоне.
5. Сделать так, чтобы регистрации считались: аналитика, которая связывает регистрацию с первой страницей, и UTM-метки на ссылках из статей в продукт.

*Первые две недели: найти спрос, а не угадывать.*
6. Выписать задачи продукта словами клиента.
7. Посмотреть спрос: Планировщик ключевых слов Google, Google Trends, подсказки в строке поиска, для русскоязычного поиска Вордстат.
8. Прочитать выдачу по каждой фразе: какие страницы там стоят.
9. Разложить фразы на те же две кучи.

*Вторая–четвёртая недели: первые страницы.*
10. Главная говорит, что делает продукт, теми словами, которые ищут: в заголовке страницы и первом заголовке на ней.
11. Три–пять узких страниц из кучи А: страница под одну задачу и сравнения с продуктами, которые люди уже знают. Широкие запросы потом.
12. Добавиться в каталоги и подборки. Для нового сайта упоминания на других сайтах ещё и способ попасть в поле зрения поисковиков.

Первые показы у новых страниц появляются через несколько недель, поэтому первый замер через четыре недели. Когда наберётся 1–3 месяца данных Search Console, переходим к обычному разбору на две кучи.

Кучу Б не удаляем, а откладываем.

## 3. Что нужно из инструментов

Чтобы начать, хватит выгрузки CSV из Search Console: «Эффективность», период три месяца, «Экспорт». В выгрузке не больше 1 000 строк на таблицу, а запросы и страницы лежат в разных таблицах. Для первого разбора этого достаточно.

Что можно добавить потом:

| Задача | Бесплатно | С оплатой за запрос | Подписка |
|---|---|---|---|
| По каким запросам нас находят | Search Console, Bing Webmaster Tools | | |
| Спрос по новым темам | Планировщик ключевых слов Google, Google Trends | DataForSEO, SE Ranking Data API | Ahrefs, Semrush |
| Кто стоит в выдаче | Открыть выдачу и прочитать первую десятку | Serper, DataForSEO | Ahrefs, Semrush |
| Кто ссылается | Search Console, Ahrefs Webmaster Tools для своего сайта | DataForSEO, SE Ranking Data API | Ahrefs, Semrush |
| Другие поисковики | Bing Webmaster Tools, IndexNow, Яндекс Вебмастер | | |
| Спрос в Яндексе | Сайт Вордстата | API Вордстата в Yandex Cloud (Search API v2) | |

Выбирайте по бюджету. Для сайта, у которого уже есть показы, хватает бесплатного. Цены меняются, актуальные и с датой проверки лежат в `references/setup.md`.

**Если ваш рынок русскоязычный.** Метод тот же: Яндекс Вебмастер играет роль Search Console, Вордстат показывает спрос. Пара важных деталей на 16.11.2026:

- API Вордстата работает через Yandex Cloud и платный: оплата за запросы, около $0,16 за 1 000 запросов по популярным фразам и динамике. Посты, где он назван бесплатным, устарели. Цену сверяйте на странице тарифов Search API.
- У Вебмастера есть свой API, для него нужен OAuth-токен Яндекса. Что он отдаёт, смотрите в его документации.
- Готовые открытые скиллы для обоих API лежат в репозитории https://github.com/artwist-polyakov/polyakov-claude-skills (автор канала «Поляков считает», лицензия MIT). Это не наш код, перед установкой посмотрите, что он делает.

Сами мы с инструментами Яндекса в этой работе не работали, поэтому детали проверяйте сами.

У любого платного API заранее ставим потолок расходов и записываем цену каждого запроса.

Отдельно про регистрации. Чтобы понимать, какая страница приводит людей, в ссылки на продукт добавляем метки (`utm_campaign` с адресом страницы, `utm_content` с местом кнопки), а при регистрации сохраняем первую метку.

## 4. Страница от запроса до «ок»

Так делается любая страница с текстом: статья, инструкция, подборка.

**До текста**

1. Читаем файл уроков с прошлых страниц.
2. Выгружаем запросы этой страницы. Слова, которые дают больше всего показов, должны остаться в заголовке и подзаголовках.
3. Если страница уже есть, сначала читаем её и сохраняем то, что работает.
4. Смотрим выдачу по главному запросу.
5. Собираем факты (раздел 5).

**Форма**

Выбираем один главный блок под задачу читателя. Он не должен повторять главный блок двух прошлых страниц. Зачем это нужно: одинаковый макет сам по себе Google не наказывает. Он отсеивает страницы, которые повторяют друг друга, и страницы, сделанные пачкой ради позиций. Один скелет на всё как раз ведёт к этому: та же страница, только с другим ключевым словом. А читатели такой блог сразу считывают как сгенерированный. Варианты, которые работают:

1. Настоящий результат: что на входе и что вышло.
2. Было и стало на одном примере.
3. Диагностика: что видишь, почему, что делать.
4. Выбор пути: два-три вопроса приводят к своему маршруту.
5. Маршрут от исходной точки читателя.
6. Готовые запросы или просьбы с результатом.
7. Шаблон, который можно скачать.
8. Открытый тест на своём материале, со своими замерами.
9. Ответ за 30 секунд и одна схема.
10. Шаги на настоящих экранах.
11. Один пример через всю страницу.
12. Расчёт времени или денег на конкретном случае.

У каждой страницы одна гипотеза: что пробуем, с чем сравниваем, когда смотрим.

**Длина:** быстрый ответ 700–900 слов, инструкция 1 000–1 500, подборка или главная страница темы 2 000–3 000.

**Текст**

- Заголовок повторяет настоящий запрос и обещает только то, что есть на странице.
- Ответ в первых 100 словах. Сразу за ним 3–5 коротких выводов вида «нужно X, делайте Y».
- Таблица сравнения, если она есть, стоит в начале.
- Подзаголовки сформулированы как вопросы читателя, со словами из запросов. Каждый раздел понятен без остальных.
- Сравнение с конкурентами только там, где заголовок обещает выбор: «лучшие», «альтернативы», «против». В инструкциях его нет.
- В конце 3–5 вопросов с короткими ответами.
- Текст не стеной: таблицы, списки, картинки. Люди листают глазами.
- Не пишем «мы протестировали», если не тестировали. Не выдумываем цифры, исследования и отзывы.

**Свой продукт в тексте**

- Ставим там, где он решает задачу читателя, и описываем путь: что сделать и что получишь.
- Один раз честно говорим, когда он не подходит.
- В подзаголовках не называем себя лучшими.
- Не обещаем результат («сэкономите пять часов»).
- Не пишем условия, которые часто меняются: бесплатный лимит, пробный период, акции. Они устаревают сразу на всех страницах.

**Призывы попробовать**

Два заметных блока с кнопкой и разным смыслом: полоса в середине и карточка в конце раздела о продукте. На кнопке написано, что человек получит, а не «Зарегистрироваться». Ссылки ведут сразу на регистрацию, а не на главную.

**Ещё**

3–5 ссылок на другие живые страницы сайта.

**Настоящий автор.** У каждой статьи есть живой человек, который её подписал. «Admin» и название компании авторами не считаются.

- Вверху подпись: имя, фото, роль, дата публикации и дата обновления.
- Короткая справка по теме: почему этот человек может об этом писать. Только то, что можно проверить.
- Ссылка, по которой об авторе можно узнать больше: профиль в LinkedIn или X, личный сайт или страница автора на вашем сайте со списком его статей. Страница автора полнее. Вариант проще: роль и ссылка на профиль рядом с именем.
- По всему блогу одни и те же несколько авторов, каждый на своих темах.
- В разметке статьи для поисковиков автор указан как человек (`Person`) с именем и ссылкой (`url`, `sameAs`).
- Фото обрезаем по голову и плечи. В кружке на 40 пикселей фото в полный рост превращается в пятно.

Честно про эффект. Google в рекомендациях о полезном контенте советует указывать точное авторство и спрашивает, есть ли у страниц подпись там, где её ждёшь. Там же он предупреждает: выдуманные имена, сгенерированные портреты и ложные регалии делают страницу ненадёжной. Роста позиций он не обещает, и мы не обещаем. Наш опыт: мы поставили настоящих авторов с ролью, фото и ссылкой на профиль по всему блогу и оставили.

Автора не выдумываем. Человек настоящий и согласен подписать страницу.

**Оглавление, по которому можно кликать.** Список «На этой странице» из подзаголовков, каждый пункт ведёт к своему разделу. Человек пришёл с одним вопросом и сразу прыгает к ответу, а не листает всё подряд. Если подзаголовки написаны как вопросы читателя, оглавление читается как список ответов.

- На компьютере оно стоит сбоку от текста и подсвечивает раздел, который сейчас читают.
- На телефоне это компактный блок вверху.
- Клик плавно прокручивает страницу и останавливается так, чтобы заголовок не прятался под шапкой сайта.
- В скилле есть готовая вставка `assets/toc.html`. Она сама собирает список из заголовков, ставится в шаблон один раз и работает на всех страницах.

**Сколько картинок.** Обложка и на страницу в 1 000–1 500 слов три-четыре картинки внутри: главный блок картинкой, цифра, которую стоит запомнить, продукт в деле. Подробности в разделе 7.

**О чём писать, когда идеи кончились**

Любую идею проверяем тремя вопросами: продукт и есть ответ? это ищут? мы можем сделать страницу лучше тех, что сейчас в топе? Проходит меньше идей, чем ждёшь. Так и задумано.

Откуда брать темы:

1. Запросы из кучи А, где страница стоит на 8–20 месте.
2. Запросы, по которым есть показы, а своей страницы нет.
3. Задачи, с которыми приходят те, кто платит. Темы вокруг этих задач сильнее тем вокруг названия категории.
4. Функции продукта, о которых никто не написал.
5. Лучшие страницы конкурентов: они показывают, какие виды страниц работают на вашем рынке.
6. Подсказки сервисов по ключевым словам. Большие цифры перепроверяем, смотрим тренд за год.
7. Длинные запросы-вопросы в Search Console.

Есть и обычные источники, которые в работе над этим скиллом не проверялись: вопросы в поддержку и на продажах, ответы в опросе при регистрации, форумы.

Виды страниц, которые подходят сайту с продуктом. Примеры для выдуманного сервиса счетов для фрилансеров:

| Вид | Пример |
|---|---|
| Как сделать дело, с продуктом внутри | «Как выставить счёт клиенту в другой валюте» |
| «X против Y» | «Наш сервис или BigBooks: что подойдёт одиночке» |
| «Альтернативы X» | «7 альтернатив BigBooks для фрилансеров» |
| «Лучшие X для такой-то аудитории» | «Лучшие сервисы счетов для фотографов» |
| Шаблон, который можно скачать | «Шаблон счёта для консультанта» |
| Мини-тул или страница под задачу | «Калькулятор пени за просрочку» |
| Расчёт денег или времени | «Во что на самом деле обходится неоплаченный счёт» |
| «Не работает? Чиним» | «Клиент пишет, что ссылка на оплату не открывается: что проверить» |
| Страница под аудиторию | «Счета для переводчиков: ставка за слово, срочность, две валюты» |
| Страница интеграции | «Счета прямо из трекера задач» |

Чего избегать. Это темы, которые приводят читателей, но не регистрации. На них часто приходится большая часть трафика:

- задачи рядом с продуктом, которые решает инструмент другого рода;
- вопросы про форматы файлов и конвертацию;
- юридические разборы «законно ли»;
- общие советы про работу с продуктом в последнем абзаце;
- вторая страница под запрос, который сайт уже закрывает.

Полная версия лежит в `references/content-ideas.md`.

## 5. Факты

Модель заполняет пробелы правдоподобными деталями. В SEO-текстах это функции, которых у конкурента нет, и возможности, которых нет у вас.

**О своём продукте** пишем по одному файлу фактов. Его собираем по самому продукту: живое приложение, страница цен, код, список изменений. Не по памяти и не по старым статьям. В файле: что продукт умеет, чего не умеет, цены и лимиты, утверждённые формулировки для чувствительных тем, список «никогда не писать», честные минусы. У каждой строки дата.

Если нужного факта в файле нет, в черновике ставим пометку «проверить» и спрашиваем. До публикации пометок не остаётся.

**О чужих продуктах** факты собирает отдельный агент. Автору нужно, чтобы фраза сложилась, а сборщику нужна только цитата. Правила сборщика:

- только официальный сайт, справка, страница цен, страницы в App Store и Google Play;
- у каждого факта дословная цитата, ссылка и дата;
- не нашёл: пишет «не подтверждено», а не догадывается.

В тексте «нет» пишем, только если это подтверждено. Иначе «не указано». Факты старше двух недель перед использованием проверяем заново.

## 6. Вычитка

Три прохода до владельца.

**Первый: другая модель в роли строгого редактора.** Пишет одна модель, вычитывает другая. Редактор возвращает оценки и цитаты мест, которые звучат как ИИ. Главная оценка «похоже на ИИ» от 1 до 10. Правим и отправляем снова, пока не станет 3 или ниже. Обычно это два-три круга.

Редактору даём запросы, факты о продукте и решения владельца, иначе он начнёт с ними спорить. Его советы не принимаем вслепую: если он предлагает факт без источника или обещание, которое нельзя давать, не берём.

**Второй: читатель.** Снимаем страницу с компьютера и с телефона. Модель изображает обычного человека, который вбил запрос и попал сюда. Листает скриншоты и говорит: нашёл ли то, за чем пришёл, где бы закрыл, попробовал бы продукт или нет.

**Третий: читаем всё сами.** Про каждый совет спрашиваем себя: что читатель сделает и что у него получится?

Потом владелец смотрит страницу такой, какой она будет на сайте, с картинками. Без его «ок» ничего не публикуется. Каждое его замечание сразу записываем в правила.

Списки слов и оборотов, которые выдают машинный текст, лежат в `references/slop-patterns.ru.md` и `slop-patterns.en.md`.

## 7. Картинки

- Модель рисует только объекты без текста. Всё, где есть буквы или интерфейс, верстаем в HTML и снимаем скриншотом. Так буквы не плывут, а продукт выглядит как настоящий.
- На картинках продукта настоящий интерфейс с правдоподобными данными, сверенный с самим продуктом.
- Скриншоты чужих продуктов: официальный сайт, окно 1440×900, без cookie-плашки, в рамке браузера и с подписью.
- Проверка на телефоне: там картинка шириной около 320 пикселей. Читаемость решаем числом слов, а не жирным шрифтом.
- В скилле лежит готовый пример обложки `assets/cover-template.html`: настоящий шрифт в HTML и место под объект от модели. Меняете цвета, шрифт и текст, снимаете скриптом. Готовую обложку смотрим ещё дважды: на ширине около 490 пикселей, как карточка в ленте блога, и на 320. Заголовок должен читаться, у краёв ничего важного.
- Обложки соседних страниц не делаем в одном формате. Чередуем: экран продукта, 3D-объект, документ крупно, цитата шрифтом, большая цифра, тёмный фон, было и стало.
- Внутри страницы одна сцена с настоящим интерфейсом или строки с иконками. Не одинаковые коробки со стрелками.

## 8. Заголовки и описания

Когда: страница на первой странице выдачи, показов много, а кликают реже, чем по другим страницам того же сайта на том же месте.

- Заголовок повторяет запрос словами человека и говорит, что внутри.
- Описание работает как короткий вывод: кому подходит, сколько стоит, в чём подвох.
- Берём небольшую пачку, 5–12 страниц. Меняем только заголовок и описание, текст не трогаем, иначе не поймём, что сработало.
- Сравниваем четыре недели до и четыре недели после.

Рабочая привычка: заголовок в 50–65 знаков, описание в 150–160. Это привычка, а не закон: Google сам решает, что показать.

Это разовая починка слабых сниппетов. Наша первая пачка заметно подняла клики, а второй круг заголовков не дал ничего.

## 9. Страницы под задачи и мини-тулы

**Страница под задачу** сделана ровно под один запрос, и человек делает дело прямо на ней: загружает файл, вставляет ссылку, получает результат. Статья объясняет, как сделать. Такая страница делает.

Когда нужна: в первой десятке по запросу стоят тулы и страницы продуктов.

Что на ней:

- заголовок, который повторяет запрос. Если у всех конкурентов в заголовке «бесплатно», а у вас не бесплатно, пишем как есть;
- рабочее окно на первом экране;
- 600–900 слов ниже: как это работает, что принимает, что получится, для кого;
- форматы и лимиты из самого продукта, а не по памяти;
- вопросы и ответы;
- ссылки на соседние страницы.

Ключевыми словами не набиваем. Если повторить запрос десятки раз на короткой странице, выше она от этого не встанет.

**Главное: передача в продукт.** То, что человек сделал на странице, должно оказаться в продукте после регистрации, без повторной загрузки. Разработчику пишем задание, а не код: что страница отдаёт, что продукт с этим делает, и по каким признакам тестировщик поймёт, что всё работает.

**Адреса и ссылки.** Главные задачи лежат в корне сайта, генераторы в `/tools/` с общей страницей-списком. Ссылки на всё это стоят в футере и в статьях. Каждая страница есть в карте сайта.

**Мини-тулы.** Небольшая бесплатная штука рядом с главной задачей продукта. Гостю даём один результат бесплатно, часть показываем сразу, остальное после регистрации на той же странице.

Страницы пачками не штампуем. Одна задача, одна страница, рабочий инструмент на ней.

Перед запуском страницу проверяет агент-тестировщик: несколько ширин экрана, светлая и тёмная тема, весь путь и все способы его сломать. После правок проверяем ещё раз, потому что правки ломают соседнее.

## 10. Сравнения

Страницы «X против Y», «альтернативы X», «лучшие X». Человек уже решил, что ему нужен инструмент, и выбирает какой. Это самые близкие к регистрации страницы.

Правило одно: пишите так, как хотели бы, чтобы конкурент написал о вас. Прямо говорите, где конкурент лучше. Таким страницам верят, и ИИ-ассистенты охотнее цитируют взвешенный текст, чем рекламу.

Обратная ошибка встречается так же часто: занизить себя.

Как устроена страница «против»:

1. Выбор в две строки: «берите X, если… / берите нас, если…».
2. Кому подходит каждый.
3. Таблица по возможностям.
4. «Где X лучше».
5. «Где лучше мы».
6. Цены конкурента с его страницы, с датой.
7. Как перейти с X.
8. Другие альтернативы.
9. Вопросы и ответы.
10. Строка внизу: «Проверено такого-то числа. Нашли ошибку? Напишите нам».

У каждой страницы свой главный блок: то одно, чем вы на самом деле отличаетесь от этого конкурента.

Факты о каждом конкуренте лежат в одном файле. Все страницы и таблицы берут их оттуда, и цена правится в одном месте. В плюсы конкурента не записываем то, что есть и у вас.

В подборках прямо говорим, какой продукт наш.

## 11. Чистка и склейка

Когда: несколько страниц сайта стоят по одному запросу и ни одна не стоит хорошо. Или на сайте много слабых страниц на темы далеко от продукта.

Перед новой страницей проверяйте дубли. Если три старые уже стоят по запросу на 20–50 месте, четвёртая не поможет. Склейте их в одну.

Собираем таблицу: адрес, клики, показы, позиция, главные запросы, ссылки с других сайтов, регистрации, тема. По каждой странице решение: убрать, склеить через 301 или оставить.

Правила, которые появились из ошибок:

1. Страницу, на которую ссылаются другие сайты, не удаляем, а перенаправляем.
2. Перед склейкой сравниваем позиции по общим запросам. Если «слабая» страница стоит выше «сильной», не склеиваем.
3. Перед правкой сохраняем копию каждой страницы.
4. Владелец утверждает весь список до первого действия.

Порядок склейки: публикуем сильную страницу, переставляем на неё внутренние ссылки, снимаем слабые, ставим 301, проверяем, что старый адрес отвечает 301 и за один переход приводит на живую страницу, отправляем старые адреса в IndexNow, проверяем карту сайта.

Замеряем отдельно страницы, которые приняли редиректы, и остальной сайт. Общий график всё смешивает.

## 12. Ссылки и каталоги

Зачем: чтобы продукт упоминали другие сайты. Каталоги и подборки «лучшие сервисы для X» читают и ИИ-ассистенты, когда их просят что-то посоветовать.

Кто что делает: агент ищет площадки, пишет тексты под каждую форму и ведёт список. Человек заполняет формы и отправляет письма.

Шаги:

1. Смотрим, где продукт уже есть. Второй профиль не заводим, поправляем старый.
2. Один раз готовим набор текстов: слоган до 60 знаков, описания на 160, 300 и 700, категории, теги, подписи к картинкам, письмо авторам подборок. Все факты из файла фактов. Тот, кто заполняет формы, от себя ничего не добавляет.
3. Идём по списку площадок.

**Зачем каталоги.** Чтобы продукт был назван и стояла ссылка на многих подходящих сайтах. Так Google и ИИ-ассистенты понимают, что продукт существует и чем он занимается. Переходы и регистрации из каталога приятный довесок, а не мерило. Карточка, с которой никто не пришёл, свою работу всё равно сделала.

Что стоит знать заранее:

- Многие каталоги ставят ссылки с пометкой nofollow. Одна карточка позиции не сдвинет. Работает сумма: одно и то же название, описание и ссылка во многих местах.
- Настоящая статья или подборка, где вас упомянули, весит больше карточки в каталоге. Делайте и то и другое.

В репозитории лежит готовый список площадок для англоязычного ИИ-продукта. В колонке `verified` записано, что мы у себя заметили по площадке: регистрации, визиты или «не замеряли». Это наблюдение, а не оценка, стоит ли туда идти.

Порядок: сначала каталоги ИИ-инструментов, их читают ассистенты. Потом каталоги программ и страницы «альтернативы такому-то». Потом площадки для запусков. В конце профили компании и каталоги попроще.

Ведите список: куда подали, что ответили, адрес готовой карточки. Когда продукт изменится, карточки придётся обновлять.

**Свои статьи на чужих площадках.** Отраслевые медиа со свободной публикацией, блог-платформы, профессиональные сети. Тут заявку никто не рассматривает, зато статья должна быть интересной сама по себе. Пишите под читателей площадки: история с выводом, а продукт внутри неё там, где он к месту. Статья из блога, вставленная как есть, обычно не работает.

Какая площадка сработает, зависит от рынка. Пример из нашей практики: для русскоязычного продукта наши статьи на vc.ru под своим именем приводили регистрации и были одним из самых сильных источников после поиска. Это опыт одного продукта, а не рейтинг площадок. Найдите ту, которую читают ваши клиенты, и проверьте её двумя-тремя статьями.

**Обмен упоминаниями.** Продукты с похожей аудиторией, которые не конкурируют, договариваются упоминать друг друга в подборках. Партнёров выбирайте по аудитории и по живому блогу, от плохого соседства отказывайтесь, и держите их немного. Со своей стороны лучше написать новую полезную подборку, чем вставлять упоминания в старые тексты.

Про риск. В правилах Google против спама среди примеров ссылочного спама есть чрезмерный обмен ссылками («ты мне, я тебе») и партнёрские страницы, сделанные только ради перекрёстных ссылок. Числа там нет. Мы читаем это так: несколько уместных взаимных упоминаний, полезных читателю, под правило не попадают, а поставленная на поток схема ради позиций попадает. Решение за владельцем.

**Чужие подборки.** Находим подборки, которые стоят на первой странице по запросам из кучи А. Пишем автору коротко и по фактам. Если в подборке о вас уже написано с ошибкой, присылаем исправление: на такие письма отвечают охотнее всего.

## 13. ИИ-поиск

Как ассистенты ранжируют ответы, снаружи не знает никто. Кто продаёт формулу, тот гадает. Известно вот что: они отвечают по страницам, которые могут открыть, и по результатам поиска, а когда просят совет, опираются на чужие списки и подборки.

Значит, работа состоит из четырёх обычных дел:

1. Не закрывать сайт от роботов, которые отвечают за поиск и за запросы пользователей.
2. Писать факты о продукте простым текстом на странице.
3. Попадать в чужие списки (раздел 12).
4. Публиковать честные сравнения (раздел 10).

**Роботы.** Проверьте `robots.txt` и выключатель «блокировать ИИ-ботов» в конструкторе сайта: иногда он включён с самого начала. Видимость в поиске и обучение моделей управляются разными роботами. Можно пускать поисковых и закрывать обучающих. Таблица роботов лежит в `references/ai-search.md`.

**`llms.txt`.** Это предложенный формат файла, который рассказывает агентам, что за сайт и где главные страницы. Честно про статус: это не стандарт. Google прямо пишет, что его поиск такие файлы не использует, а держать файл для других систем можно. В документации роботов OpenAI и Anthropic он не упомянут. Держать его стоит, если это дёшево: агенты, которые его всё-таки читают, получат верные факты.

Главный риск в том, что файл устаревает молча. Проверяйте его при каждой смене цен и функций и после каждой чистки. И сначала посмотрите, не создаёт ли ваш конструктор сайта этот файл сам.

Оценку «видимости в ИИ» не считаем. Честных замеров два: переходы с доменов ассистентов в аналитике и отчёт AI Performance в Bing Webmaster Tools.

## 14. Замер и откат

Каждую правку записываем: дата, адрес, что поменяли, где копия, первая проверка через неделю, вторая через три.

Как мерить:

- сравниваем целые недели с целыми неделями, чтобы совпадали дни недели;
- смотрим позицию вместе с кликами;
- новой странице даём 2–4 недели до первых показов.

Чего ждать: после большой правки Google оценивает страницу заново, и 1–4 недели показы и клики могут проседать. Это нормально. Проверка через неделю нужна, чтобы убедиться, что ничего не сломалось.

**Правило отката.** Через три недели:

- кликов меньше на 30% и больше, и позиция не возвращается: ставим старую версию из копии;
- кликов меньше, но позиция неделя за неделей растёт: ждём ещё две недели;
- иначе оставляем.

Позиции и клики дают ранний сигнал. Итог считаем по регистрациям со страницы. Выборки маленькие, выводы делаем только при заметной разнице.

После каждой страницы записываем два пункта: что получилось лучше и что в следующий раз сделать иначе. Следующая страница начинается с чтения этого списка.

## 15. Публикация

Работа скилла заканчивается на «ок» владельца. Как страница попадёт на сайт, решает он. Вставить текст руками тоже нормально.

Если публикует агент:

- старая версия сохранена целиком;
- адрес страницы с трафиком не меняем;
- публикуем только эту страницу. Кнопку «опубликовать весь сайт» агент не нажимает: вместе с вашей правкой уедут чужие недоделанные;
- новую страницу сначала заводим черновиком.

После публикации: смотрим живую страницу на трёх ширинах и листаем до конца, отправляем адрес в IndexNow, владелец нажимает «Запросить индексирование» в Search Console (программно это сделать нельзя), проверяем карту сайта.

## 16. Проверка старых страниц

Вычитка из раздела 6 нужна новому черновику. А страницы, которые висят на сайте месяцами, проверяем отдельно. Особенно те, что делались быстро и пачками.

Не всё проверяем одинаково глубоко. Сначала страницы из кучи А с показами и страницы, где упомянут изменившийся факт. На большом сайте сначала гоняем по всем страницам дешёвые механические проверки, а читаем только главные.

Что смотрим на каждой странице:

1. **Как звучит.** Отдаём текст второй модели, записываем оценку «похоже на ИИ» и цитаты. Выше 3: в список правок.
2. **Помогает ли сделать дело.** Ответ на первом экране? Вступление с конкретики или с общих слов? В подборке все пункты настоящие?
3. **Как выглядит на телефоне.** Скрипт снимает страницу на трёх ширинах и предупреждает, если она ездит вбок. Смотрим: таблицы, которые вылезают за экран, картинки с нечитаемым текстом, сколько листать до первого призыва, сломанную вёрстку.
4. **Что влияет на регистрации.** Продукт стоит там, где он решает шаг читателя. Два заметных блока с кнопкой и разным смыслом. На кнопке написано, что человек получит. Ссылки ведут на регистрацию и с метками.
5. **Факты.** Каждое утверждение о продукте сверяем с файлом фактов: цены, названия тарифов, лимиты, функции. Заглядываем в разметку для поисковиков и в описание страницы: устаревшее прячется там.
6. **Ссылки.** Ссылки на блоги конкурентов и посторонние сайты убираем. Официальные сайты конкурентов оставляем. Ищем мёртвые внутренние ссылки и старые варианты своего домена.
7. **Автор.** Настоящий человек с фото, ролью и ссылкой на профиль.
8. **Мелочи.** Прошлый год в заголовке, незагруженные картинки.

Итог для владельца: таблица, по строке на страницу, проблемы по важности. Сначала неверные и устаревшие факты, потом то, что мешает читать или регистрироваться, потом машинный текст, потом мелочи. У каждой страницы предложение: быстро поправить, переписать, склеить или оставить.

Правки начинаем после «ок» владельца и как обычно: копия, правка, запись. Механические правки не смешиваем с переписыванием текста на той же странице, иначе замер ничего не скажет.

На странице, которая уже стоит в выдаче, чиним, а не переписываем: структуру подзаголовков, адрес, рабочие ссылки и картинки не трогаем.

## 17. Заметки, которые не теряются

Сессия закончилась, и память агента пропала. Что записано в файлы, осталось. Поэтому всё лежит в папке `seo/` в вашем проекте:

```
seo/
  README.md          строка на каждый файл и папку
  site-profile.md    продукт, кто платит, две кучи, постоянные решения владельца
  change-log.md      каждая правка, её копия, даты проверок, результаты
  lessons.md         что в следующий раз сделать иначе
  product-facts.md   единственный источник для всего, что пишется о продукте
  experiments.md     по одной гипотезе на страницу
  sources/           факты о чужих продуктах: цитата, ссылка, дата
  backups/           старые версии изменённых страниц
  audits/            отчёты о проверке страниц
  listings/          тексты для каталогов и список площадок
```

При первом запуске скилл добавляет короткий блок в `CLAUDE.md` или `AGENTS.md` вашего проекта: где лежат заметки по SEO, что читать первым, откуда брать факты о продукте и что без «ок» владельца ничего не публикуется. Этот файл агент читает в начале любой сессии, даже если сам скилл не подключился.

Решения записываем сразу, как только они приняты, а не в конце работы.

## 18. Следим за продуктом

Страницы устаревают, когда продукт меняется, а текстам об этом никто не сказал.

При настройке скилл спрашивает две вещи:

- Какая у вас аналитика и как её читать: через подключение у агента, через API или по вашим выгрузкам. PostHog, GA4, Plausible, Mixpanel, Amplitude, подойдёт любая. Нужна одна таблица: страница входа или кампания и число регистраций.
- Где видны изменения продукта: публичный список изменений, трекер задач, история репозитория. Или просто вопрос владельцу: «что вышло или поменялось с такого-то числа?»

В начале каждой сессии агент смотрит, что изменилось с даты прошлой проверки. Берёт только то, что заметит читатель: цены и тарифы, лимиты, новые и убранные функции, новые названия. Обновляет файл фактов, у каждой строки ставит дату. Потом ищет старые значения на живых страницах, в `llms.txt` и в разметке и выдаёт список страниц на проверку.

Новая функция, которая решает задачу, которую люди ищут, заодно становится идеей для страницы.

## 19. Частые ошибки

**С чего начинают**
- Работают с темами, которые дают клики, но не регистрации. Сначала две кучи.
- Берут тему по большой цифре спроса и не смотрят тренд за год.
- Принимают сезонный спад за проблему страницы.
- Публикуют количеством. Шаблонные статьи только под спрос почти ничего не дают. Чистка и склейка слабых страниц часто помогает сайту больше, чем новые.

**Факты**
- Берут факты о продукте из старого снимка кода или старых текстов. У каждого факта должны быть дата и названный источник правды.
- Не проверяют заново факты о конкурентах. Через пару недель они уже другие.
- Записывают конкуренту в плюс то, что есть и у своего продукта.
- Пишут «умеет всё это» и ошибаются в деталях. Каждое «всё» и «любой» проверяем отдельно.
- Ставят в текст цифру из данных пользователей.

**Текст и картинки**
- Делают все страницы на один скелет и все обложки на один макет. По одной они смотрятся нормально, а подряд выглядят сгенерированными.
- Рисуют схемы из одинаковых коробок со стрелками. Одна сцена с настоящим интерфейсом объясняет больше.
- Дают примеру, который идёт через всю страницу, разъехаться между картинкой, скриншотом и текстом.
- Проверяют таблицы и картинки только на компьютере. На телефоне ссылка в ячейке таблицы может съехать.
- Оставляют смысловые ошибки редактору. Спросите про каждый совет: что читатель сделает и что у него получится?

**Заголовки**
- Превращают правку заголовков в привычку. Первая починка слабых сниппетов может заметно поднять клики, второй круг часто не даёт ничего.
- Пишут заголовок, не перечитав страницу.

**Чистка**
- Удаляют страницу, которую обещали партнёру держать на сайте. Нужен список таких страниц.
- Клеят страницу к той, которая стоит ниже по общим запросам.
- Удаляют страницу, на которую ссылаются другие сайты. Её надо перенаправлять.
- Ждут, что карта сайта обновится сама. В некоторых конструкторах она обновляется только при публикации всего сайта.
- Чистят без копий. Вернуть страницу можно, только если все её поля сохранены заранее.

**Страницы под задачи и мини-тулы**
- Оставляют тулы без ссылок с сайта и без карты сайта. Трафика из поиска у таких нет.
- Проверяют страницу один раз. Правки ломают соседнее, после них нужна повторная проверка.
- Проверяют блок страницы отдельно от сайта. Общие стили сайта могут его сломать.
- Обещают на странице то, что верно не во всех режимах запуска.

**Старые страницы**
- Проверяют все страницы одинаково глубоко. Дешёвые механические проверки гоняем по всем, читаем только главные.
- Считают устаревший факт проблемой одной страницы. Страницы пишут друг с друга, и одно и то же старое значение стоит по всему сайту и в разметке.
- Переписывают страницу, которой хватило бы починки.

**Ссылки, каталоги, ИИ-поиск**
- Не записывают, куда подали заявки. Через пару месяцев не отличить «не подавали» от «отказали».
- Копируют в новые карточки старую ошибку: не тот домен, устаревшую цифру.
- Судят о каталоге по переходам. Его задача в другом: чтобы продукт был назван и стояла ссылка.
- Забывают про `llms.txt`. Продукт поменялся, а файл описывает старый.
- Заменяют живой `llms.txt` от конструктора сайта своим застывшим.

**Замер и публикация**
- Откатывают через неделю. После переписывания страница часто проседает на несколько недель и потом восстанавливается. У нас одна пачка переписанных страниц в итоге встала намного выше прежнего. Решаем через три недели.
- Смотрят общий график по сайту. Одна страница со всплеском или провалом прячет всё остальное.
- Меняют на странице несколько вещей сразу и не могут понять, что сработало.
- Публикуют весь сайт ради одной страницы. Вместе с ней уезжают чужие недоделанные правки.
- Публикуют поздно вечером на сайте с другим часовым поясом и получают завтрашнюю дату.
- Держат решения в переписке. Новая сессия их не знает, поэтому всё записываем в файлы.
